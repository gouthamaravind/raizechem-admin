# Technical Audit Report: Raizechem Admin ERP

**Date:** 2026-05-24  
**Auditor:** Gemini CLI  
**Project Version:** 1.1.4

---

## 1. Executive Summary
This audit provides a deep dive into the mathematical, logical, and structural integrity of the Raizechem Admin ERP. The system is architecturally sound, utilizing **Atomic RPCs** for critical financial state changes. However, several "soft spots" in mathematical precision, concurrency handling for non-invoice transactions, and TypeScript safety have been identified.

---

## 2. Mathematical & Financial Audit

### 2.1 Floating Point Precision (Medium Risk)
- **Issue**: Frontend GST calculations (`src/lib/gst.ts`) use standard JS `number` types and `Math.round`. 
- **Risk**: Repeated calculations or complex splits (CGST/SGST) may result in penny variances between the UI display and the backend's `numeric` rounding.
- **Recommendation**: Standardize on a "Paise-first" (integer) calculation or use a big-decimal library for the frontend.

### 2.2 Hardcoded Fiscal Year Logic (Low Risk)
- **Issue**: Backend RPCs (`create_invoice_atomic`) hardcode the FY start to April:
  ```sql
  IF EXTRACT(MONTH FROM CURRENT_DATE) >= 4 THEN v_year := EXTRACT(YEAR FROM CURRENT_DATE)::int;
  ```
- **Risk**: If the business ever operates on a different FY calendar (e.g., Jan-Dec), the numbering series will break logic.
- **Recommendation**: Dynamic FY lookup from the `financial_years` table.

### 2.3 Discount Persistence Gap (Medium Risk)
- **Issue**: The `Invoices.tsx` UI supports line-level discounts, but the `create_invoice_atomic` RPC does not appear to persist `discount_pct` or `discount_amount` into the database items.
- **Status**: **Incomplete**.

## 3. Logical & Concurrency Audit

### 3.1 Non-Atomic Order/PO Creation (Medium Risk)
- **Issue**: While Invoices use an Atomic RPC with `FOR UPDATE` locks, Sales Orders and Purchase Orders rely on standard Supabase client-side logic.
- **Risk**: High-concurrency environments could result in duplicate sequential numbers (e.g., two `ORD/2026/042` records).
- **Recommendation**: Port Order/PO creation to Atomic RPCs.

### 3.2 Branch Isolation (Low Risk)
- **Issue**: Multi-branch support is implemented via `branch_id`, but the global `company_settings` table acts as a contention point for *all* branches during invoice generation.
- **Risk**: Performance bottleneck for large multi-branch organizations.
- **Recommendation**: Move sequential counters to a `branch_settings` table.

### 3.3 Void Operation Integrity (Verified)
- **Finding**: Voids correctly handle stock reversal, ledger entry reversals, and status updates via Atomic RPCs.
- **Edge Case**: If a payment is voided *after* a partial refund has been issued against it, the system needs to ensure the refund is also accounted for (Requires deeper DB trigger analysis).

---

## 4. Mobile & Field Ops Audit

### 4.1 Offline Sync Logic (High Quality)
- **Finding**: `useFieldOps.tsx` implements a robust `PendingAction` queue in `localStorage`.
- **Note**: The system handles "Offline-like" errors gracefully and retry-syncs upon reconnection.

### 4.2 GPS Data Retention (Low Risk)
- **Finding**: Data is pruned via a 30-day `location-cleanup` edge function.
- **Recommendation**: Ensure the user is notified of data expiration for audit purposes.

---

## 5. Technical Debt & Type Safety

### 5.1 Excessive `as any` Casting
- **Finding**: Over 140+ instances of `as any` in the codebase, primarily around Supabase RPC calls and complex object mapping.
- **Impact**: Higher risk of runtime crashes (blank screens) as TypeScript's protection is bypassed.

### 5.2 Error Boundaries
- **Finding**: Missing app-wide or module-specific Error Boundaries.
- **Impact**: A single component failure (e.g., in a chart or table) crashes the entire page.

---

## 6. Security Audit (RLS & RBAC)

- **Frontend**: Enforced via `RoleGuard` in `App.tsx` and `useAuth` hook.
- **Backend**: All tables have RLS enabled using `has_role()` and `has_any_role()` helpers.
- **Observation**: The `profiles` table insertion is correctly restricted, relying on database triggers from `auth.users`.

---

## 7. Action Items (Prioritized)

1.  **High**: Create `create_order_atomic` and `create_po_atomic` RPCs to prevent numbering collisions.
2.  **Medium**: Update `create_invoice_atomic` to support and persist line-level discounts.
3.  **Medium**: Refactor `src/lib/gst.ts` for higher precision.
4.  **Low**: Implement Error Boundaries across main module routes.
